# Feature Intake — 기능 요청 접수 & 기획 정합성 체크

새 기능을 요청받았을 때, 코드를 작성하기 전에 **기획 문서와의 정합성을 먼저 확인**하고 시각 자료를 만들어주는 게이트입니다. [[deep-interview]]가 "요구사항이 충분히 명확한가"를 점수화한다면, 이 스킬은 "이게 game-design.md에 이미 있는 기능인가, 있다면 문서와 일치하는가"를 확인하는 데 집중합니다. 둘 다 트리거되는 요청이면 game-design.md 대조를 먼저 하고, 그 결과로 좁혀진 질문만 deep-interview 방식으로 물어봅니다 — 같은 걸 두 번 묻지 않습니다.

## 언제 활성화되는가 (트리거)

사용자 메시지가 **새 기능/시스템을 만들어달라는 의도**로 읽힐 때:

- "OOO 기능 필요해" / "OOO 기능이 필요한데"
- "OOO 만들어줘" / "OOO 추가해줘" / "OOO 구현해줘"
- "OOO 어떻게 만들까" / "OOO 어떻게 구현하지" / "OOO 어떻게 만들어야 할까"
- 영어 표현도 동일하게: "I need a feature for X", "build me X", "how should I implement X"

## 활성화하지 않는 경우 (제외)

- **버그 수정** — "에러", "버그", "크래시", "고쳐줘", "NullReference", "안 돼요" 등이 언급된 경우 → `/unity-fix` 영역
- **후속 구현** — 이 대화에서 이미 요구사항/디자인이 확정된 기능을 실제로 코딩해달라는 요청
- **명시적 opt-out** — `--skip-interview`, "그냥 해줘", "묻지 말고 해줘"
- **단순 수치/스타일 조정** — "속도 좀 높여줘", "색 바꿔줘" — 새 기능이 아님
- **10단어 미만의 아주 짧고 명백한 요청** ("점프 추가해줘" 같은) — 다만 game-design.md 대조는 여전히 유효하면 1단계만 짧게 수행

## 1단계 — game-design.md 대조

1. `.claude/docs/game-design.md`를 **읽습니다**. `.claude/docs/game-design-v2.md`처럼 버전이 붙은 파일이 별도로 있다면 같이 확인하고, 내용이 다르면 더 최신 버전(파일 상단의 "버전"/"작성일" 표기 기준)을 기준으로 삼습니다.
   - **파일 자체가 없다면:** 진행을 멈추고 사용자에게 묻습니다 — "이 프로젝트에는 game-design.md가 없습니다. 기획 문서 없이 바로 진행할까요, 아니면 먼저 이 기능에 대한 기획을 정리할까요?"
2. 요청한 기능이 문서에 이미 있는지 확인합니다 (Grep으로 관련 키워드 검색 + 주변 문맥 읽기):
   - **이미 있음:** 해당 섹션을 인용하고, 요청 내용이 문서와 일치하는지 확인합니다. 문서에 없는 새로운 요구사항(스코프 확장, 다른 동작)이 섞여 있다면 짚어줍니다.
   - **전혀 없음:** "이 기능은 game-design.md 범위 밖입니다"라고 알리고, 그대로 진행할지 / 먼저 기획 문서에 반영할지 확인합니다.
   - **부분적으로만 있음:** 문서에 있는 부분과 없는 부분을 나눠서 제시합니다.

## 2단계 — 필요한 추가 질문

1단계 결과 아직 불명확한 것만 묻습니다. 문서에 이미 답이 있는 내용은 다시 묻지 않습니다. 참고할 축(이 프로젝트 아키텍처 기준):

- 이 기능이 건드리는 기존 시스템은? (예: WeaponSystem, ZoneSystem, BehaviorTree, Blackboard)
- 런타임에 변하는 상태값이 있다면 어디에 둘 것인가 — SO에 두면 안 됨 (`.claude/rules/architecture.md`의 "데이터 분리 규칙" 참고), Blackboard/런타임 클론 인스턴스여야 함
- 플레이어 전용/AI(봇) 전용/공유 서브시스템 중 무엇인가
- 빈번하게 생성/삭제되는 오브젝트(발사체, 이펙트, 에너미)가 관련되면 Object Pool 대상인가
- 성능 예산에 영향이 있는가 (매 프레임 로직, 드로우콜 등)

질문은 최대 3~4개, 실제로 구현 방향을 바꿀 수 있는 것만. 이미 충분히 명확하면 이 단계는 건너뛰고 바로 3단계로.

## 3단계 — 플로우차트/다이어그램 시각화

두 가지를 모두 만듭니다 (형식이 다른 별개의 산출물입니다):

1. **인라인 시각화** — `mcp__visualize__read_me`를 먼저 호출해 컨텍스트를 읽은 뒤, `mcp__visualize__show_widget`(diagram 모듈)로 이 기능의 흐름(상태 전이, 시스템 간 데이터 흐름, BT 노드 구조 등 기능 성격에 맞는 형태)을 지금 대화창에 바로 보여줍니다.
2. **머메이드 소스** — 같은 내용을 Mermaid 코드 블록(`flowchart`, `sequenceDiagram`, `stateDiagram-v2` 중 적합한 것)으로도 작성합니다. 이건 이후 game-design.md나 PRD에 그대로 붙여넣을 수 있는 형태여야 하며, 채팅에 텍스트로도 보여줍니다.

## 4단계 — PRD 작성 여부 확인

다이어그램을 보여준 뒤 사용자에게 묻습니다: **"이 기능에 대한 PRD(제품 요구사항 정의서)도 작성해드릴까요?"**

- **Yes:** 아래 템플릿으로 작성하고, `.claude/docs/prd/<feature-slug>.md`로 저장할지 제안합니다.
- **No:** 여기서 종료합니다. 실제 구현으로 넘어가려면 `/unity-feature`나 `/unity-workflow`를 쓰라고 안내합니다.

### PRD 형식

`.claude/skills/feature-intake/example-prd.md`에 있는 형식을 **반드시 그대로 준수**합니다:

- 섹션 타이틀 6개(`## 1. What` ~ `## 6. Tech Stack`)는 이름과 순서를 바꾸지 않습니다. 예시 파일의 "포모도로 타이머" 내용은 형식 참고용일 뿐이며, 실제 내용은 이번에 요청받은 Unity 기능에 맞게 채웁니다 (예: `## 6. Tech Stack` → 웹 프레임워크 대신 관련 Unity 서브시스템/데이터 위치/성능 제약).
- 3단계에서 만든 Mermaid 다이어그램은 예시 파일의 "다이어그램" 섹션 형식(`### 예시 A: ... (Flowchart)` / `### 예시 B: ... (Sequence Diagram)`)을 따라 PRD 맨 아래에 첨부합니다 — 상태 전환 위주면 flowchart, 시스템 간 주고받는 데이터/호출 순서 위주면 sequence diagram을 선택합니다.

## 규칙

- 1→4단계 순서를 지키되, 이미 답이 명확한 단계는 짧게 요약만 하고 넘어갑니다. 매 단계를 억지로 길게 끌지 않습니다.
- game-design.md는 이 프로젝트의 source of truth입니다 (`CLAUDE.md`, `.claude/rules/architecture.md`가 그렇게 정의). 요청이 문서와 충돌하면 반드시 짚고 넘어갑니다 — 조용히 무시하지 않습니다.
- 이 스킬은 **브리프/다이어그램/PRD까지만** 만듭니다. 실제 코드 구현·씬 작업은 `/unity-feature`, `/unity-workflow`, `unity-coder` 에이전트에 위임합니다.
- 사용자가 이미 상세하게 설명했다면 이미 명확한 내용을 다시 묻지 않습니다.
